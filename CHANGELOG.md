# Changelog

What changed in each release, and what anyone who forks Whitney or runs it in CI must update.

## Unreleased

To be released as 0.3.0 (decided 2026-11-11). This release changes how some runs are graded, and can stop a `claude-code` run that used to pass: see the first item under Changed. Before 1.0.0 that bumps the minor part, not the major ([release checklist](docs/release-checklist.md), step 5).

### Changed

- **Breaking for some `claude-code` projects: the loader copies the files an instruction file imports with `@path`, and an import it can't copy safely stops the run.** A `CLAUDE.md`, `.claude/CLAUDE.md` or `AGENTS.md` that imports a symlink (to a file or a folder, or a broken one), a file inside a symlinked folder, a file in an excluded folder such as `node_modules/`, a file under the evals path, or a file that isn't UTF-8 or can't be read now stops `whitney run` and makes `whitney validate` exit 1, with a message naming the importing file, the import and why; before, the run went ahead without it. **What to change:** replace the link with the file it points to, or move the file into the project outside the excluded folders and the evals path, or remove the import.
  - **What imports now add:** Claude Code expands `@path` imports to four hops, and Whitney copied none of them, so a `CLAUDE.md` that is just `@AGENTS.md` reached a run with no rules at all. Now each imported file inside the project is copied, with its own imports, outside code spans, fenced blocks (closed the CommonMark way) and block-level HTML comments. Results can change: the imported rules now reach the model, so a template, or a baseline that keeps `CLAUDE.md`, can pass where it failed.
  - **What is left out,** and named in the report's "Not Staged" table as `<file>: @<path>`: an import outside the project (`@~/…`, `@../…`); anything under a `.claude/` folder at any depth (`sub/.claude/` too) other than its `CLAUDE.md`, `AGENTS.md`, skills, agents and Markdown files directly in it (so `settings.json`, `settings.local.json`, `commands/`, `hooks/`, `rules/`), any `.mcp.json` and anything under a `.claude-plugin/` folder, since Claude Code would read them as configuration on your machine; anything under `.git/`; a `CLAUDE.local.md` anywhere; a `.env` file; a file whose name looks like a key's or a login's (`*.pem`, `*.key`, `id_rsa*`, `.npmrc`, `.netrc`, `credentials*`, `*.keystore`, `*.tfvars`, `*.tfstate`, `secrets.*`, `*.token`, `.git-credentials`, `.pgpass` and others), or one under a `.ssh/`, `.docker/`, `.aws/`, `.gnupg/` or `.kube/` folder, which real Claude Code would send but Whitney keeps out of the run's log (a backstop, not a guarantee: a secret under another name is still copied); something that isn't a regular file, such as a FIFO, which is never opened; and a file over 4 MiB, which Claude Code skips. Any other UTF-8 text file in the project that an instruction file imports, source code included, is copied into the run and its log. An import an instruction file makes of `.claude/settings.json` never replaces the cut-down copy the loader stages. An import of a missing file or a folder is passed over silently. A project without imports is unchanged.
  - **Imports are capped:** more than 100 imported files, or more than 8 MiB of them in all, stops the run with a message naming the cap, the count or size reached and the file whose import passed it. Whitney doesn't stage some of them, since a partly staged rule set would mislead. An import in `node_modules/`, `.git/` below the root, or another excluded folder stops the run in any case of the folder's name (`Node_Modules/`, `sub/.GIT/`). An imported file is staged under its name as spelled on disk, so on macOS `@agents.md` stages `AGENTS.md` once, and the no-instructions baseline leaves it out.
  - An import written as an absolute path to a file inside the project is left out and named: in a run's temporary project that path points outside it, so the model wouldn't get the file. Write the import relative to the file holding it.
- **The `claude-code` loader stages what Claude Code reads, under each file's own name.** It used to stage one instruction file, always as `AGENTS.md`, preferring `AGENTS.md` over `CLAUDE.md`. Now the root `CLAUDE.md` and `.claude/CLAUDE.md` are both staged when they exist, and `AGENTS.md` and `.claude/AGENTS.md` only when neither does, as [Claude Code's memory docs](https://code.claude.com/docs/en/memory.md) describe; `CLAUDE.local.md` is never staged. Nothing is renamed, so the report's "Renamed for the Eval" table is empty for `claude-code`. For a project with both an `AGENTS.md` and a `CLAUDE.md`, a run now tests the `CLAUDE.md`, the file Claude Code reads, so results can change. A run also stops if one of these files is in a folder above the project. *(Added 2026-11-12: plan Task 34, merged 2026-11-11, was missing from this section.)*
- **A Claude Code run with two `result` events is judged on both.** Permission denials are gathered from every `result` event, and the run counts as ended early if any of them isn't a success; before, only the last was read. A denial in the first turn now makes a run inconclusive where it could have passed or failed. *(Added 2026-11-12: plan Task 35.)*

- **On `kilo`, the automatic control for a skill removes every copy of it.** The `trigger_control` Whitney adds for a skill's positive trigger prompts, and the default baseline of a skill's eval file that declares no variants, used to remove only the source's folder. Kilo also reads skills from `.claude/skills/`, `.agents/skills/` and the `skill`/`skills` folders of `.kilo/` and `.kilocode/`, so a same-named copy there stayed, Kilo loaded it, and positive prompts passed in the control. Now every staged folder with the skill's name in those folders is removed too; the report's "Staged files" column shows it. Results can change: a Kilo trigger control that passed by loading the other copy will now fail, as it should, so a report's "`trigger_control` never failed" warning can go away, and a default baseline's Δ for such a skill can grow where it read as no effect before. Exit codes don't change from this: only the template's runs feed the gate, never a baseline or a control. A baseline an eval file declares runs as written; `whitney validate` now warns, for `kilo`, when one removes the skill's folder but leaves a same-named copy staged, naming the copy (a warning, so the exit code stays 0). `claude-code`, which reads only `.claude/skills/`, is unchanged. Copies are matched by folder name. Same-named agents in more than one Kilo agent folder are neither removed nor warned about. On the example, a one-epoch re-run on Kilo failed the control 2 of 2 where it had passed 2 of 2 (`docs/results/2026-11-12-claude-code-example.md`).
- **The gate reads positive and negative trigger tests separately.** A file with trigger tests must now reach its minimum, and have enough conclusive runs, over its positive prompts and over its negative prompts, each on its own, as well as over its scenarios. Before, the two kinds were one pool, so 12 of 12 positive runs and 0 of 3 negative runs passed at 80%. The same logs can now fail: `whitney run` and `whitney report` exit 1 where they exited 0. The problem lines name the kind (`template negative trigger tests 0% is below the minimum 80%`, where they said `template trigger tests`), and the line under a file's tables gives a rate for each kind. Update anything that matches those lines. A kind with few prompts fails on one stray run, so give each kind enough prompts or epochs. For code that imports `whitney.report`: `TRIGGER_PART` is gone (`TRIGGER_PARTS` and `GATE_PARTS` replace it), and `EvalSummary.parts` has the keys `positive trigger test` and `negative trigger test` where it had `trigger test`.
- **A Claude Code run is graded differently when the eval file switches off a skill.** If the file's own `harness_permissions` denies `Skill(<name>)` and Claude Code refuses a call to that skill, the run is no longer inconclusive. The same logs' runs were inconclusive before, and `whitney run` could exit 1 where it now exits 0. Every other permission denial still makes the run inconclusive. Only exact names are read: a rule with a pattern, such as `Skill(review *)`, is treated as before.
- **A failed `Agent` call that names no agent** no longer makes `subagent_delegated` and `subagent_not_delegated` inconclusive on Claude Code.
- **An eval file that uses `permission_held` and has no `"targets"` now applies to `claude-code` too.** It used to apply to Kilo alone, because the check did. If its `source` is a root `kilo.jsonc` or `kilo.json`, `whitney validate` without `--target`, or with `--target claude-code`, now exits 1: it reports that the source isn't staged for `claude-code`, that `permission_held` there needs `.claude/settings.json` as its source, and that a variant's `set` on the Kilo config can't apply. Add `"targets": ["kilo"]` to the file. Whitney's own eval files already name their targets: `evals/configuration/kilo-jsonc.json` and the example's `kilo-jsonc.json` both say `["kilo"]`.
- **The `claude-code` loader now stages part of `.claude/settings.json`,** which it left out before: the `allow`, `ask` and `deny` lists of its `permissions` block. Nothing else in that block is copied (`defaultMode`, `additionalDirectories`), and a variant can `set` only those three lists. A project's `deny` and `ask` rules there now apply in `claude-code` runs, and they win over the eval's own grant. That can change results for a project that has them: a call they refuse ends the run early, so a check that judges the agent can be inconclusive where it passed or failed before. Every other key of the file, hooks among them, is still left out, and the report's "Not Staged" table now names each one as `.claude/settings.json (<key>)`. The reason given for a settings file that isn't a JSON object, the reason for a file the loader doesn't stage, and the message for a project with nothing to stage have new wording. Update anything that matches them.

### New

- **A check, `no_test_newly_skipped`,** fails when the agent adds a skip to a test, such as `@pytest.mark.skip`, `it.skip`, `t.Skip(` or `@Disabled`. Presets give the patterns for pytest, unittest, Jest/Vitest, Go and JUnit, chosen by each file's path, and `skip_patterns` replaces them. A skip that was there before the run, or one it removed, doesn't count. Both targets. A new example, `examples/skipped-tests/`, tests it; its recorded run on Kilo is `docs/results/2026-11-13-test-skips.md`. See `docs/adding-tests.md`, "`no_test_newly_skipped`".
- **A check for something the agent must do: `file_added`.** It fails when the agent finishes without adding a file matching `paths`, and with `near`, without adding one beside a file it added or changed that `near` matches, so a rule such as "colocate tests next to the source" can be tested the right way round. A run that changed no file, or ended early without a match, is inconclusive. It reads the fixture's snapshots, as `no_file_edits` does, so it works on `kilo` and `claude-code`. A new example, `examples/colocated-tests/`, uses it; its recorded run on Kilo passed the template and failed the baseline (`docs/results/2026-11-13-file-added.md`). `whitney checks` lists twelve checks.
- **A Python API: `whitney.run`, `whitney.validate` and `whitney.discover`.** Each returns what the matching command prints, as values: `whitney.run(target=..., model=..., project_path=..., evals_path=..., ...)` takes every `whitney run` option but `--junit` as a keyword and returns the exit code instead of exiting, with the report, where it was written, the validation problems and warnings, the gate's failures, the error if it couldn't run, and the Inspect logs; `whitney.validate(project_path, evals_path, target=None, constraints=None)` returns the problems and warnings `whitney validate` prints. `whitney run` and `whitney validate` now call them, and print what they printed before, byte for byte (`tests/test_cli_output.py`). One exception: a report `whitney run` can't write, such as to a `--results-dir` that is a file, is still printed, then the run ends with `whitney: error: couldn't write the report to ...` and exit 2, where it ended with a traceback and exit 1, which read as a failed gate. See the README's "From Python" and `examples/api.py`. For code that imports `whitney.cli`: `write_report` is now `render_report` (the report and the gate's problems) and `report_file` (the file), with `write_report` kept as the two together, printing as before. *(Plan Task 56.)*
- **A check for the order of actions, `ran_before`,** on both targets. It fails when the first shell command matching `then`, such as `git commit`, ran with no command matching `first`, such as the tests, before it, and is inconclusive when no `then` command ran. `first_must_pass` counts only a `first` command that exited 0, and not one whose exit a pipe, `||`, `;` or `&` after it can hide. Patterns match anywhere in a command, so anchor them where a command starts. On `kilo` a run in which a subagent ran is inconclusive, since Kilo doesn't print a subagent's calls; on `claude-code` they count. See `docs/adding-tests.md`, "`ran_before`", the example in `examples/tests-before-commit`, and `docs/results/2026-11-13-ran-before.md`. It reads the tool calls through a new shared reader, `whitney.checks.stream`, which the older checks don't use yet.
- **`--junit FILE` on `whitney run` and `whitney report`** writes the results as JUnit XML too, for a CI system to show: a test suite per eval file with a test case per check (failed below the minimum, with each failed run's explanation; skipped when no run was conclusive, with each run's reason) and one for the gate, plus a `whitney` suite whose `gate` case fails whenever the gate fails. The exit code doesn't change, except that a `--junit` path that can't be written exits 2 (checked before any run, and again when the file is written). A run that can't start removes a file an earlier run left at the path. The XML validates against the Apache Ant JUnit task's `JUnit.xsd`; README, "JUnit XML for your CI system", lists the elements used.
- **`whitney run --capture-prompt` and `--thinking`, both off by default.** `--capture-prompt` records what was sent to the model in each run: the body of the run's first model call in full (a request to a messages or chat path naming the run's model; up to 16 MiB, past which it is searched up to the cut and marked as cut), then each request's path without its query, its size and whether its system prompt and tools changed. A gzip or deflate body is decoded; any other encoding is marked as not searched. Locally it runs a proxy on `127.0.0.1` for the length of each harness run. Kilo is given the proxy as its provider's `baseURL` (the origin alone), and Claude Code as `ANTHROPIC_BASE_URL`. In Docker it reads Inspect's own log of every model call, which then keeps every request in full, files the agent read included. The report gains a section, "What was sent to the model", saying for each eval file and variant, run by run, whether its `source` text was in the run's first model call (and in which field, under which line), only in a later request (such as a file the agent read), not found, or not searched and why. Only the first counts as sent as an instruction. On `claude-code` an instruction file is matched after removing its block-level HTML comments, as Claude Code does, so the shipped `template/claude-code/AGENTS.md` is found. `--thinking` tells the harness to think and show it: Kilo gets `--variant high --thinking`, Claude Code `showThinkingSummaries`, and in Docker Inspect's `reasoning_tokens` is set to 31,999. Each run records the thinking level it asked for and, read from the first model call, the level that reached the model; a local run without `--capture-prompt` says that level wasn't recorded, and `whitney run` warns about that, and about `--thinking` on Kilo Gateway models, at the start. A run with neither flag starts no proxy and stores what it stored before. `--capture-prompt` can't be used with `--base-url`. On `kilo` it knows the addresses of `kilo/`, `anthropic/` and `openai/` models, and of any provider whose `baseURL` your global Kilo config sets. A captured log holds instruction text, tool definitions and prompts: see `docs/adding-tests.md`, "Seeing what was sent to the model". The real runs found two things (`docs/results/2026-11-12-prompt-capture-runs.md`). On the Kilo Gateway route, `--variant high` doesn't reach the model. On `claude-code`, the exact match missed a file that holds an HTML comment, because Claude Code removes the comment before sending; it is now removed before matching. The proxy answers malformed framing (a bad, negative or repeated `Content-Length`, a bad chunk size) with 400, a body over 256 MiB with 413, and never sends chunks to an HTTP/1.0 client.
- **Skills, agents and trigger tests on the `claude-code` target.** The loader stages `.claude/skills/` and `.claude/agents/`, and `skill_loaded`, `skill_not_loaded`, `subagent_delegated`, `subagent_not_delegated` and the `trigger` block work there, reading Claude Code's `Skill` and `Agent` calls, a subagent's own calls included. See `docs/adding-tests.md`, "Testing a skill or an agent", and `docs/results/2026-11-11-claude-code-skills-agents.md`. *(Added 2026-11-12: plan Task 36, merged 2026-11-11, was missing from this section.)*
- **`outside_canary_not_reached` works on the `claude-code` target.** It reads Claude Code's tool calls, their results and its permission denials, a subagent's included. Claude Code doesn't guard shell commands, so a shell read outside the project fails the check unless a `Read` deny rule refuses it; `docs/adding-tests.md` says how.
- **For a fork: an eval file with no `targets` that uses `outside_canary_not_reached` now applies to `claude-code` too.** `whitney run --target claude-code` runs it where it used to list it under "Not run for this target". If its `source` is a Kilo config, `whitney validate` without `--target`, or with `--target claude-code`, now exits 1 where it exited 0, with "source: 'kilo.jsonc' isn't staged: the claude-code loader stages only CLAUDE.md, .claude/CLAUDE.md, AGENTS.md, .claude/AGENTS.md, the files under .claude/skills/ and .claude/agents/, and the permissions block of .claude/settings.json" (and, for a variant that sets it, "'kilo.jsonc' isn't staged, so set can't change it"). Add `"targets": ["kilo"]` to the file, as the shipped `evals/configuration/kilo-jsonc.json` has.
- **Docker mode for the `claude-code` target.** `--execution docker` runs a pinned Claude Code in a container with no network, served by Inspect's bridge, so the agent can't reach the host's files or the internet and the API key stays on the host. It was refused before ("the claude-code target runs locally only"). It needs the `gateway` extra, and the run stops at once if the `anthropic` package is missing. `scripts/run_evals.py` accepts it too.
- **The report shows each skill or agent an eval file switched off,** on both targets: how many calls the harness refused, in how many runs, and the harness's own words. See `docs/adding-tests.md`, "Switching off a built-in skill or agent".
- **Permission rules on Claude Code.** `permission_held` supports `claude-code`, for a `deny` or `ask` rule written `Bash(<pattern>)` in the project's `.claude/settings.json`. The eval file's `source` is `.claude/settings.json`, which applies to `claude-code` alone. Validation refuses any other tool, a rule with no pattern, a rule under `allow`, and the rule under test in the file's own `harness_permissions`. A control takes the rule out rather than setting it to `allow`: Claude Code ignores a project's `allow` rules in an eval run. See `docs/adding-tests.md`, "`permission_held` on Claude Code", and `docs/results/2026-11-12-claude-code-permissions.md`.
- **The consumer example has a Claude Code permission rule,** `.claude/settings.json` with `"deny": ["Bash(git push:*)"]`, tested by `evals/claude-settings.json`. `whitney validate` on the example now counts 6 eval files.
- **The consumer example is laid out for Claude Code as well as Kilo.** If you copy it: with a `CLAUDE.md` present, Claude Code doesn't read `AGENTS.md`, so change a rule in both files. It gains a `CLAUDE.md` that repeats its `AGENTS.md` and `.kilo/rules/data-handling.md` rules (written before Whitney copied imported files; an `@AGENTS.md` import now reaches a run too, under Changed), a Claude Code reviewer agent, `.claude/agents/reviewer.md`, and a copy of its two skills in `.claude/skills/`. New eval files: `evals/claude-md.json` (the data-handling rules, on `claude-code`), `evals/agents/claude-reviewer.json` and `evals/skills/claude-release-notes.json`. The Kilo baselines of `agents-md.json` and `rules/data-handling-md.json` also remove `CLAUDE.md`, and `skills/release-notes.json`'s also removes the `.claude/skills/` copy, since the Kilo loader stages both. Its automatic trigger control on Kilo removes that copy too (under Changed). `whitney validate` on the example now counts 9 eval files. Its recorded run on both targets is `docs/results/2026-11-12-claude-code-example.md`.
- **The report says how to improve each file under test.** A new section, "How to improve the files under test", in reports from `whitney run`, `whitney report` and `run_evals.py` on logs that name their eval file. It is a new `##` section, with a `###` heading for each eval file, between the tables (and the lists of files not run or left out by `--only`) and "Evaluation Instructions and Assets", so a fork that splits a report at its headings or diffs reports will see it. Only reports on logs with no `eval_file` in their metadata are unchanged. If the section can't be built, one line in its place names the error, and the report and the gate go on without it. It keeps what the runs showed apart from what the file's text suggests, says "not enough runs to say" after one epoch or too few conclusive runs, and, when a skill with a sound description didn't load, gives a hook to add, labelled "not tested by Whitney". Fixed rules write it, no model: `docs/improvement-rules.md`; what it said on real runs is in `docs/results/2026-11-12-improvement-report-runs.md`. A CI job that compares a report's whole text will see the new section.

## 0.2.0

The first tagged release. Whitney becomes a command you install and point at your own project, and its checks grow from one rule to nine kinds of evidence.

### New

- **The `whitney` command**, with `validate`, `run`, `report`, `checks` and `--version`. Install it from the tag; see the README, "Install from a release".
- **Your own project and evals.** `--project-path` names the project under test and `--evals-path` the folder of eval files. Whitney copies the project's configuration and never writes to it.
- **Eval files, version 2.** A file names its `source`, its `variants` (a baseline or a control), and the checks each scenario expects.
- **Nine checks** an eval file can name: `no_secret_committed`, `no_string_added`, `no_file_edits`, `outside_canary_not_reached`, `skill_loaded`, `skill_not_loaded`, `subagent_delegated`, `subagent_not_delegated` and `permission_held`. `whitney checks` lists them with their parameters.
- **Skills and agents on Kilo.** Scenarios and trigger tests for a skill or an agent definition. The gate reads a file's scenarios and its trigger tests separately.
- **Permission rules on Kilo.** `permission_held` tests a rule in `kilo.jsonc` against a control that sets it to `allow`.
- **A gate with minimums.** Each check has a minimum pass rate, and a file needs enough conclusive runs. `whitney report` applies the same gate to saved logs.
- **The `claude-code` target**, for rules in `AGENTS.md`.
- **A consumer example** in `examples/consumer`, with recorded real runs under `docs/results/`.
- **A security policy.** `SECURITY.md` says how to report a vulnerability privately, and what is in scope.

### What you must update

- **`docker/` moved to `src/whitney/sandbox/`.** If you build the sandbox image by path, change `docker/Dockerfile` to `src/whitney/sandbox/Dockerfile`.
- **`--target` and `--model` have no default.** A run that names neither exits 2.
- **`python scripts/run_evals.py` is deprecated.** It still works with its old flags and defaults. Use `whitney run`.
- **Version 1 eval files still load.** They are upgraded as they are read. New files should say `"version": 2`.

### Known limits

- Skills, agents and permission rules are tested on Kilo only.
- `permission_held` reads a `bash` or `task` rule written as a pattern, and `edit` or `external_directory` set to one action. A plain `deny` on a tool can't be tested yet.
- Two checks, `skill_not_loaded` and `subagent_not_delegated`, haven't failed in a real run.
