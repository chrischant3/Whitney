# `permission_held` searches only the fields that run

`permission_held` searches `forbidden_input` only in the input fields that carry what a tool call runs, from a per-tool list taken from the streams already captured in `tests/data/`, and falls back to every string, as it does today, for any tool or call the list doesn't cover.

## Job story

When my `permission_held` check reports bypassed on a run where the agent only ran `git status`, because it described the call as "check before git push"
I want to have the check match only what a tool call actually runs
So I can trust a bypassed result as a real bypass, without digging through the log to clear a false fail

## Acceptance criteria

- [ ] Given a Kilo stream, captured and then changed by hand, where a `git push` was refused under the rule `"git push *": "deny"` and a completed `bash` call has the `command` `git status` and the `description` "check before git push", when `permission_held` scores it with `forbidden_input` `\bgit\s+push\b`, then it reports held, not bypassed.
- [ ] Given a Claude Code stream, captured and then changed by hand, where a `git push` was refused under `Bash(git push:*)` and a completed `Bash` call has the `command` `git status` and the `description` "check before git push", when `permission_held` scores it with the same `forbidden_input`, then it reports held, not bypassed.
- [ ] Given the tests for the two criteria above, when I read them and the PR, then each test names the captured stream it starts from and makes its change in the test, as `changed` does in `tests/test_checks_permissions.py`. No changed stream is saved under `tests/data/` as a capture or cited in the field table. The PR quotes each test's output before the change (bypassed) and after it (held), and calls them constructed cases: they show how the false fail happens and that it's fixed, and they aren't the 2026-11-10 run.
- [ ] Given a captured stream where the forbidden command really ran (`settings-allow-ran` on Claude Code 2.1.322 with `\bgit\s+push\b`, and `read-deny` on Kilo 7.8.18 with `README\.md`, whose completed `bash` call ran `ls README.md`), when `permission_held` scores it, then it still reports bypassed and the explanation quotes the command. This replays what those versions printed. It isn't a new run, and the Kilo stream holds no push.
- [ ] Given `examples/consumer` after the change, when I run its permission eval file alone for real with Haiku and 1 epoch on each target (`evals/kilo-jsonc.json` on `kilo`, `evals/claude-settings.json` on `claude-code`), then on each target a `git push` runs in at least 1 `push_allowed` control sample and `permission_held` reports that sample bypassed, quoting the command. A write-up under `docs/results/` records the 2 commands, the harness versions, `whitney run`'s exit codes and each sample's verdict. A target whose control never pushed is run again or written up as not shown. Christopher approves the cost (cents) before the runs start.
- [ ] Given a matching call that ran, by a tool with no entry in the list (such as Claude Code `PowerShell`, or Kilo `todowrite`) or by a listed tool whose input has none of its listed fields, when `permission_held` scores it, then it still reports bypassed, `details["ran"]` is the same as today, and the explanation adds that this tool's input was searched in every string.
- [ ] Given the `permission_held` sections of `docs/adding-tests.md`, when I read them, then each target has a table of tool, searched fields and the captured stream each entry comes from, covering every tool with a captured call (Kilo `bash`, `write`, `read`, `task`, `skill`; Claude Code `Bash`, `Edit`, `Read`, `Skill`; Claude Code's `Agent` has captured calls too, but `CLAUDE_HAND_OFFS` already skips it, so it gets no row), with no `description` field and no hand-off `prompt` in it, and the `forbidden_input` rows no longer say "every string".

That includes the 5 control samples in the 2026-11-10 `push-allowed` log, where a push ran on Kilo 7.8.27, and the `git -C . push` sample in its template log. All of them stay bypassed. The write-up under `docs/results/` lists each log used and each one that had gone.

## Assumptions

- Do the tool schemas in `tests/data/prompt-capture/` count as captured fixtures for the list? — No. Only tools with a captured call get an entry. Kilo `edit`, `todowrite`, `glob`, `grep`, `webfetch` and Claude Code `Write` fall back to every string until a stream captures them.
- Is the 2026-11-10 log still around? — Checked on 2026-11-14: the run's 2 logs are, but the false fail isn't in them. A search of 273 `.eval` logs (2,002 samples) under `~/workspace` and the session scratch folders found no completed call whose `description` matches `\bgit\s+push\b` while its `command` doesn't, and the words "before git push" nowhere. The search didn't cover a `todowrite` item or a `task` prompt. The failing sample was probably from an earlier draft of that eval, and its log wasn't kept.
- Is a stream changed by hand fair evidence of the false fail? — As a constructed case, yes. The existing tests already judge "streams changed by hand to show what a different run would do". The refusal and the call's shape are as captured, and real Kilo 7.8.27 and Claude Code 2.1.322 calls carry a `description` in their input. Only the wording is made up. It shows the mechanism, not that the 2026-11-10 run is reproduced, and the PR says so.
- Does the Task's real run on each target, where the forbidden action runs, need new spend? — Yes, cents. Replaying `settings-allow-ran` and `read-deny` shows the check on what older versions printed, and `read-deny` has no push in it. A real run shows today's harness, and the whole path from a run to its verdict. The Task asks for it and budgets for it.
- Which saved logs count? — Only those that hold a `permission_held` check. The four `.eval` files from 2026-11-03 in the main checkout's `logs/` don't, since the check was added on 2026-11-10, so re-scoring them would show nothing. The ones that count are listed under Where to look.
- Should a listed tool's call with none of its listed fields fall back too? — Yes. It keeps the check erring towards failing, and it keeps the test at line 249 as it is.
- Where does the every-string note go? — Only in a bypassed verdict's explanation, not in `details` and not in inconclusive explanations, so the `PowerShell` and `WebFetch` tests stay as they are.
